Security

Security model

The promise is narrow: the agent never holds the SSH key or password, never opens an SSH connection, and runs only what you allowed, with the output masked before it leaves the console.

You approve the policy and decide every ticket in lox run, outside the agent. The console runs in an account and a container the agent cannot read or drive.

Skills, rules and MCP tool descriptions only guide the agent; the console’s checks are the guarantee. This page summarises the full security model.

The boundary between the agent and the console is the operating system’s: separate accounts, the kernel’s peer credentials on the socket, separate containers. The lockkit console framework holds it; lockssh adds the SSH side.

What lockssh enforces

No shell, no climbing, no options

The remote line is exec followed by the quoted argv: exec 'systemctl' 'status' 'nginx'. Nothing after it in the line can run, and an argv[0] that starts with - or + is refused.

In an allow rule, a glob never matches an argument that starts with - or +, so it cannot choose an option you never wrote: git log * does not allow git log --output=/home/u/.bashrc. A glob never covers a . or .. segment, so cat /var/log/* does not reach /etc/shadow.

The SSH account’s login shell must be a POSIX shell (sh, dash, bash, ksh, zsh): another one may read the quoted arguments differently.

Production profiles

  • A command outside the allow list is a write, and a write on production is always a human’s decision: auto.exec = "auto" (and auto = "full-auto") is refused when the policy loads.
  • Its tickets carry the prod-write risk.
  • Trusting a new host key takes the last 8 characters of its fingerprint, typed.
  • A root login is refused.

What is not masked

The default detectors find cards, emails, IBANs, public IP addresses, phone numbers and secrets (password=..., tokens, PEM keys, URL userinfo). They do not find person names, postal addresses, free-text personal data, or secrets without a known shape or label: those reach the agent.

Command output can be anything. Prefer commands whose output you know (status, counts, metrics) over reading files, and add mask rules for the project’s own identifiers in .lockssh/pii.toml.

What Docker does and does not separate

The agent’s container holds no key, has no SSH connection and reaches the console only through the socket. A process that is neither the console account nor in lockssh-clients (nor an allowed uid) is refused.

Your own account is another matter: whoever can run docker commands can attach to the console, exec into it or open its home volume. An agent that runs shell commands as you usually can. For that boundary, run the agent in a container of its own without the Docker socket, as lea does. Details.

What lockssh does not do

  • It does not know what a program does. A program that runs other programs or writes files from its arguments (find -exec, awk, less, vim, tar, sudo, env, sh -c, xargs, git with hooks) turns a narrow rule into a shell. Allow such programs only with literal arguments. The policy review warns; its list is a safety net, not a complete one.
  • It does not resolve paths on the host. A rule’s path is text: a symlink under an allowed directory reads wherever it points.
  • It does not confine the SSH account. What a command can do is what the account can do: give it only the rights the allow list needs.
  • It does not mask what its detectors miss (above).
  • It does not prevent exfiltration by an allowed command. An allowed command that sends data elsewhere (curl, a mail command) does so.
  • It does not separate you from your own account (above).
